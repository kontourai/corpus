# Changelog

## 0.7.0

- Neutralise GitHub expressions and ignore untokenisable CLI commands; treat settings-only and empty pnpm workspace definitions as root-only repos.
- Parse npm aliases and GitHub dependency forms; use YAML workspace/workflow evidence, reject empty pnpm workspaces and heredoc/nested run mentions, and support package-manager CLI forms, composite actions, and optional bin metadata.
- Verify v2 builtOn per package against external runtime and workspace Kontour dependencies; exclude root/workspace package names, support declared product groupings through via arrays, and reject duplicate declarations, warn on dev-only use, and report explicit skips. Support reasoned CLI invocation evidence in manifests and bundles.

## Unreleased — Corpus

- **Store conformance: host vectors.** A conformance vector may declare `"scope": "host"` when it needs behavior a store library does not implement. `search-working-set` is the only one: it moves out of corpus-store's expected-fail list, which could otherwise never become empty, and becomes an obligation that every host mounting the store must pass. `@kontourai/corpus-conformance` exports `storeVectors`, `hostVectors` and `vectorScope`; an unknown scope fails at import. corpus-store's runner executes only store vectors (123), refuses a selected host vector, and fails if its expected-fail list names one. The list drops from 20 to 19 entries.
- **`check --json` and `check --only`.** `--json` prints the result as one JSON object on stdout (`schemaVersion: 1`) with a `verdict` (`pass`, `warn`, or `fail`), the exit code, numeric `summary` counts, each gate's status and messages, `staleDocuments`, and `actions`; exit codes are unchanged, and any run that does not reach a gate result (an unknown or blank option, a bad `--only`, a missing manifest, `--help`, or an internal error) still prints one `fail` object with `error` and exit 2. Each stale document is labelled with its kind, `docs-covers`, lists every covered file that changed, and appears once in `actions` with `type: "docs-covers"`, so a stale document no longer looks like a broken link. The shape is the one a Veritas external-tool evidence check reads. `--only <gates>` (comma-separated) runs only those gates plus the manifest. An unknown name, or a selected gate that cannot run (`freshness` without `--base`, `decisions` without a `decisions` block, `adr-freeze` without `--base` and `decisions.adr`), is a usage error (exit 2), and so is `--base` or `--advisory` when no selected gate reads it. The text report is unchanged when neither flag is passed.
- **Static bundle source and topic hierarchy.** `corpus mcp --bundle <file>` (repeatable) serves prebuilt `docs-bundle.json` files as they are: read and validated once at startup, never rebuilt or refetched. A malformed bundle, an unreadable file, or two bundles for one product is a usage error (exit 2). The library exports `staticSource(bundles)`, which a host passes to `createDocsServer`, plus `bundleFileSource` and `bundleShapeError`. Bundle topics gain three optional fields, `parentId` (another topic's `id` in the same bundle), `tags`, and `summary`; the hub and bundle sources refuse a dangling or cyclic `parentId` and a repeated topic `id`. `list_topics` returns them and takes an optional `parentId` filter; `search` scores tags at 3 and summaries at 2 and returns the fields on topic matches. `digest` includes the fields only when a topic has them, so existing bundles keep their digests. `corpus build` does not write the fields yet, and no existing tool name or argument changed.
- **The root package is published to npm.** `@kontourai/corpus` gets its own trusted-publishing workflow, `publish-npm-corpus.yml`, separate from the workspace prerelease workflow. It is dispatched on `main` with an exact version that must equal `package.json` and be the first `CHANGELOG.md` section with no `Unreleased` section left. It publishes stable versions to `latest` and prereleases to `next`, and it publishes, with provenance, the exact tarball that a `contents: read` job packed, checked against a file allow-list, installed with `--ignore-scripts`, and ran (`corpus check`, `corpus decisions check`, and the `docs-kit` alias), handed over with a SHA-256 check against both the artifact's `SHA256SUMS` and a hash the verify job passes as a job output. The workspace workflow `publish-npm.yml` gets the same job-output check. The release preflight refuses an `Unreleased` heading at any level, bracketed or not. The publish guard now accepts `@kontourai/corpus`. `npm run verify:pack` runs the packed-consumer check, and CI runs it. Consumers should move from GitHub tarball installs to an exact-pinned dev dependency with a lockfile (`npm install --save-dev --save-exact @kontourai/corpus@<version>`) once a version is published; the tarball form remains for unreleased commits. The README's MCP and adoption examples now use the npm package.
- **builtOn evidence follow-ups.** An unparseable line in a package script or workflow `run:` block (a bad `${…}` substitution, a bare `${`, or a `${{` that never closes) no longer discards the rest of the block: scripts are tokenised per logical line (continuations and open quotes joined), only that line is skipped, and a CLI declaration that then lacks evidence says how many command lines were skipped as unparseable and where. A `}}` inside a single-quoted string no longer ends a `${{ … }}` expression early. In `pnpm-workspace.yaml`, `packages: ['.']` (the root package) and a list of only exclusions are treated as a single-package repo instead of exiting `2`; a list that also has another inclusion glob still exits `2` when none resolve. `pnpm <bin>@1` and `yarn <bin>@1` are now tested as non-evidence.
- **Decision registry ergonomics** ([#22](https://github.com/kontourai/corpus/issues/22), [#23](https://github.com/kontourai/corpus/issues/23)). With `decisions` declared, every `*.md` directly in `decisions.dir` (the records and the index) is reachable without a `documents` entry, so adding a record no longer needs a `corpus.json` edit. They are still published only when listed. `corpus decisions index` now writes an index that `documents` already lists but that does not exist yet; every other command still fails on that missing file, and the command still refuses any other missing document. The ADR freeze now lets `README.md` and `index.md` be added directly in `decisions.adr.dir`; every other added file still fails, including a rename to a new path. `@kontourai/corpus-conformance` adds a vector for each of the five secret detectors that had none, and two vectors that pin how a subject spanning several lines is read.
- **Decision registry gate.** A v2 `corpus.json` may declare `"decisions": { "dir", "index", "adr": { "dir" } }` (every key optional). When it does, `check` and `build` run a `decisions` gate: every `<dir>/*.md` except the index must be a valid topic-keyed decision record (statuses `current`, `superseded`, `merged`, `needs-decision`; required `subject`, `decided`, and `evidence`; relations to existing slugs; no secret-shaped refs; no unknown keys), and the index must be fresh. With `decisions.adr`, `check --base` also runs `adr-freeze`, which fails on any file added under the frozen ADR directory. New commands: `corpus decisions check [--base]` runs only these gates, and `corpus decisions index` writes the index and nothing else. The JSON Schema ships as `schemas/decision-record.schema.json`, and `@kontourai/corpus-conformance` gains `decision-records.json`. Compared with the per-repository checker this replaces, unknown frontmatter keys, duplicate keys, symlinked records, and subjects whose value contains a line break are now refused (a subject written over several lines that YAML folds into one line is accepted), `supersedes` must be a list, frontmatter is parsed as YAML (an unquoted `#` begins a comment; other differences are listed in the doc), and the index header names `corpus decisions index` and the Corpus format document. Repositories without a `decisions` block are unaffected. See [docs/decisions.md](docs/decisions.md).
- **Breaking: v1 manifests are refused.** Corpus reads only a schema v2 `corpus.json`. A `docs-kit.json`, alone or next to a `corpus.json`, is a usage error (exit 2) in `check`, `build`, `locate`, `init`, and `mcp --repo`; the message names the file and says to rename it to `corpus.json`, set `"schemaVersion": 2`, and add `purpose` and `builtOn` (or, next to a `corpus.json`, to delete it). A `corpus.json` with `schemaVersion: 1` fails the manifest gate (exit 2), and `purpose` and `builtOn` are always required. The v1 deprecation warning and the `purpose` and `builtOn` gates' v1 skips are gone. `mcp --workspace` discovers only subdirectories with `corpus.json` and skips one with only `docs-kit.json`, noting it once on stderr. `build` therefore writes only v2 `docs-bundle.json`; the bundle format is unchanged, and readers (`mcp --hub`, the hub page) still accept published v1 bundles. `products.json` keeps its own `schemaVersion: 1`. To migrate, rename `docs-kit.json` to `corpus.json`, set `"schemaVersion": 2`, and add a one-sentence `purpose` and a `builtOn` list (empty if the product builds on no other Kontour product).
- `corpus init` now scaffolds a schema v2 `corpus.json` (with a `purpose` placeholder and an empty `builtOn`) instead of a v1 `docs-kit.json`. A new `purpose` gate in `check` fails with exit 1 when `purpose` is exactly that placeholder, so it cannot reach `docs-bundle.json`; `build` is blocked by it too. `init` still refuses to overwrite a manifest of either name (the v1 read path was later removed; see the breaking entry above). The missing-manifest error now names `corpus.json` and suggests `corpus init`.
- The MCP initialization response's `serverInfo.name` is now `corpus` (previously `docs-kit`), under both CLI bins. In this repository, only the MCP server-identity test keys on that name; production tool lookup uses the unchanged tool names. External clients that explicitly match `serverInfo.name === "docs-kit"` must update that match; arbitrary external consumers have not been audited. Station's shared MCP connection code records the negotiated name as metadata rather than using it to route docs tools.
- The root package is `@kontourai/corpus`, with `corpus` and compatible `docs-kit` bins. Preferred v2 `corpus.json` manifests add required purpose and public-contract building blocks; v1 bundles remain readable (v1 manifests were later refused; see the breaking entry above). This repo has since migrated to its own v2 `corpus.json`.
- Public store conformance vectors require `MISSING_EVIDENCE` for duplicate IDs, including reuse after retirement. The runner rejects malformed expected entries without `equals` or `length`.

## 0.6.0

Additive: v0.5.0 manifests stay valid, `products.json` is unchanged, and the bundle gains two optional per-document fields.

- **Select text, then ask, challenge, or edit.** Every page now loads `docs-kit.js`, a static template script with no dependencies, and its CSS in `docs-kit.css`. Selecting text in the page content shows a toolbar: **Ask** (Alt+A) and **Challenge** (Alt+C) copy a prompt for your agent with the product, repository, `path:start-end@sha`, section heading, page URL and anchor, and the quoted selection, telling the agent to call the MCP `locate` tool and read the source code. **Open issue** opens a prefilled `issues/new` URL, labelled `docs-challenge`, with the quote in a code fence (so selected `@names` notify no one) and capped at 8,000 characters by truncating the quote. **Edit** opens `edit/<branch>/<path>#L<start>`. Alt+T focuses the toolbar. It has an `aria-live` toast, a selectable-textarea dialog when the clipboard is unavailable, touch placement below the selection, light and dark themes, and no animation under `prefers-reduced-motion`. Selected text is only ever set as text, never as HTML. Pages without content changes now contain this one script tag.
- **Source provenance in the HTML.** `<main>` carries `data-src-path`, `data-src-sha`, `data-repo`, `data-product`, `data-title`, `data-branch`, and `data-selection-primary`. Top-level paragraphs, headings, code blocks, and blockquotes, each item of a top-level list, and each row of a top-level table carry `data-src-line="<start>-<end>"`: 1-based source-file lines, still correct after front matter is stripped. The sanitizer allows exactly `data-src-line`, and docs-kit removes it from a document's raw HTML, so provenance comes only from the build.
- **Manifest fields.** Optional `branch` (a valid git branch name, default `main`) for Edit links, and optional `selectionActions: { "primary": "ask" | "challenge-issue" }` for the leading toolbar action. Both are validated strictly (exit 2).
- **MCP `locate` tool.** `locate {product, quote, source?}` finds a quoted passage in a product's documents, tolerating whitespace, Markdown formatting, and punctuation, and returns the source path, file line range, sha, enclosing heading and anchor, surrounding Markdown, a GitHub blob URL with `#Lstart-Lend`, a `confidence`, and, when the quote is ambiguous, `matchCount` and up to 10 `alternatives`. Text in code is matched as the page shows it.
- **Bundle.** Each document gains `repoPath` (its path from the git top level) and `lineOffset` (front-matter lines stripped), so `locate` reports file lines. Both are optional for readers, and `digest` is unchanged.
- **Optional WebMCP tools.** Where the browser exposes `document.modelContext` (or the older `navigator.modelContext`), the page registers `get_selection_context`, `search_docs`, and `get_topic`, with an `AbortSignal`, and does nothing when the API is absent or fails. WebMCP is a Chromium-only draft.
- **Tests.** `npm run test:browser` drives the toolbar and the WebMCP tools in headless Chromium through `playwright-core` (a dev dependency). It needs a Chromium for playwright-core and is not part of `npm test`.

## 0.5.0

Additive: v0.4.0 manifests stay valid, and the bundle and `products.json` formats are unchanged.

- **Redirect stubs keep the URL fragment.** A meta refresh drops `#fragment`, so `old.html#section` used to land at the top of the new page. Each stub now has a small inline script, before the meta refresh, that calls `location.replace` with the target plus the incoming fragment. A target that has its own `#anchor` keeps it, and the incoming fragment is ignored. The meta refresh, `rel="canonical"`, `noindex`, and the visible link stay, so a browser without JavaScript still redirects (without the fragment). The target is embedded with `JSON.stringify`, with every `<` escaped as `\u003c` and U+2028 and U+2029 as `\u2028` and `\u2029`, so no target can close the script element. Stubs are no longer script-free; a site with a Content Security Policy that forbids inline script falls back to the meta refresh.
- **Generated-site check covers the stub script.** `build` fails (exit 1) when a redirect stub lacks exactly one redirect script, or when the script's target is missing or differs from the meta refresh URL.

## 0.4.0

Additive for manifests: v0.3.0 manifests stay valid. A new gate can fail a repository that passed before, and the bundle gains documents that have no page.

- **Bundle-only documents.** A `documents[]` entry accepts `"publish": false` (a boolean). The document gets no page, navigation entry, or landing card, but stays in `docs-bundle.json`, so the MCP server serves it and topics may point at it. Its bundle `url` is the GitHub blob URL at the built sha, and its `markdown`, and topic Markdown taken from it, has relative links made absolute: published targets go to their page URL, images and other embedded files (`src`, `srcset`, `poster`) to `raw.githubusercontent.com`, anything else to its GitHub blob page. Published pages that link to it get the blob URL. Every `check` gate still applies to it, and reachability counts it as listed. A redirect to it fails the `redirects` gate. The bundle `digest` is computed over the Markdown as written, so it still ignores the sha and base URL.
- **`paths` gate.** `check` (and therefore `build`) fails with exit 1 on absolute home-directory paths (`/Users/<name>/`, `/home/<name>/`, `C:\Users\<name>\`) anywhere in the landing page or a listed document, bundle-only ones included, and reports each as `file:line`. `/Users/Shared/` and `/home/runner/` are not personal and are exempt. The optional top-level `allowLocalPaths` lists exact document paths to skip; a glob, a path that is not a document, or a repeat is a manifest error (exit 2).
- **Topic error wording.** A topic whose source is not listed now says "is not listed" rather than "is not published", since a bundle-only document is a valid topic source.

## 0.3.0

Additive: v0.2.0 manifests stay valid, and the bundle and `products.json` formats are unchanged.

- **Redirects.** An optional top-level `redirects` object in `docs-kit.json` maps old site-relative `.html` paths to a published source (`path` or `path#anchor`) or an absolute `https://` URL. `build` writes a stub at each old path with an immediate meta refresh, `rel="canonical"`, `noindex`, a visible link, and no script, using relative URLs from the stub's own directory. Stubs are listed in `.docs-kit-build`, and the generated-site check verifies their links and refresh URLs. Because GitHub Pages serves `x.html` for `/x`, a key also covers the extensionless URL. `docs-bundle.json` does not change.
- **`redirects` gate.** `check` fails (exit 1) when a redirect target is missing or unpublished, its anchor does not resolve, or a key repeats or collides with a page or file docs-kit generates. Malformed keys and values are manifest errors (exit 2). `build` also refuses a stub that would overwrite a copied asset. Keys are compared after Unicode NFC normalization and case folding, and an `https://` target is written in its parsed, normalized form.

## 0.2.0

Improvements from the first adoptions. Every change is additive: v0.1.0 manifests stay valid, and the bundle and `products.json` formats are unchanged.

- **Mermaid diagrams.** A fenced ` ```mermaid ` block now renders as `<pre class="mermaid">` instead of a code block. Pages that contain one load Mermaid 12.1.0 from jsDelivr with an SRI `integrity` hash and `crossorigin="anonymous"`, using `securityLevel: 'strict'` and a theme that follows `prefers-color-scheme`. Pages without one load no script. A `script` written in Markdown is still stripped, and `docs-bundle.json` keeps the Markdown as written.
- **Document title override.** A `documents[]` entry in `docs-kit.json` accepts an optional `title`, a non-empty string. It replaces the H1-derived title in the navigation, landing cards, the page `<title>`, and `docs-bundle.json` (so it changes the bundle `digest`).
- **Raw-HTML titles.** A document without a Markdown H1 takes its title from the first raw-HTML `<h1>` that has text, before falling back to the file name.
- **YAML front matter.** A leading `---` block closed by `---` or `...` within the first 2000 lines, holding at least one top-level `key:` line, is stripped before link and anchor checks, rendering, topics, and the bundle `markdown`, so Jekyll-era docs no longer render an `<hr>` and a stray heading. Check failures keep source-file line numbers. A simple `title:` in the front matter is used when the document has no Markdown or raw-HTML H1. An unclosed block, or one with no key line (a thematic break followed by prose and another `---`), is left as written. A leading UTF-8 BOM is dropped, so it no longer hides front matter or a first-line heading.
- **Landing page `<title>`.** It is now `<title> — <tagline>` when a tagline is set, and still `<title> documentation` otherwise.
- **Docs.** The README now says what the topics gate enforces: a topic anchor must be a heading outside blockquotes and lists, at any level.

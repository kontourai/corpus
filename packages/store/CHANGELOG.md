# Corpus Store and Conformance changelog

`@kontourai/corpus-store` and `@kontourai/corpus-conformance` are released together, at one version, through the [workspace publish workflow](../../README.md#publishing-the-store-workspaces). Prereleases use the npm `next` dist-tag. The root `@kontourai/corpus` CLI has its own [changelog](../../CHANGELOG.md).

Until `0.1.0-next.5`, these entries lived in the root changelog's unreleased section. Each is listed under the first prerelease published from `main` after it merged. Pull requests that had no entry at the time are listed by title.

## 0.1.0-next.5

- **corpus-store: constructing and reading the default store creates nothing in an existing root.** `KitDefaultStoreAdapter` no longer creates `records/` in its constructor, and a read that finds no `records/` directory answers empty without writing `graph-index.json` or `alias-index.json`, so a host's dry run (for example the Knowledge kit's `dream --dry-run`) leaves the root as it found it. The first write creates `records/` and the indexes as before. A root that does not exist yet is still created and bound at construction.

## 0.1.0-next.4

- Add a host-authorized, exact-record reviewed-confidence snapshot and conditional update with evidence revisions and durable replay receipts. Purge retires receipts tied to erased targets or evidence. Hosts authenticate reviewers and bind decisions; the store does not infer human authority.
- Clarify store erasure results and retained reasons. A record purge identifies an exact readable proposal id under `NOT_FOUND`, and root initialization reports a non-private `coordinationDirectory` without disguising it as a root-binding mismatch.

## 0.1.0-next.3

- **corpus-store: preview a purge before you confirm it** ([#69](https://github.com/kontourai/corpus/issues/69)). A host can now see exactly what an erasure will remove before it asks a person to confirm, and the erasure refuses if the store changed after they looked. `KnowledgeStorePurger` gains `previewPurge(ids)` and `previewPurgeProposal(proposalId)`. They return the lists the erasure will return (records erased, the cascade, records that keep other support, records that only refer to them, proposals rejected, scrubbed or blocked, and the record behind an applied proposal) as ids and states only, without writing (beyond finishing a transaction an earlier crash left half done, as every read does) and without `allowPurge`. They run the same planning code as `purge` and `purgeProposal`, which are now split into plan and commit, so a preview equals the committed result unless the store changed in between. Each preview carries a `revision`. `purge` and `purgeProposal` take an optional `{ expectedRevision }` and, if any record, proposal, request key or externally edited note has changed since, throw `StaleRevisionError` (`code: 'STALE_REVISION'`, new in `KnowledgeStoreErrorCode`) and write nothing; preview again and confirm the new effects. Without `expectedRevision` both behave as before. A root with no identity marker cannot be previewed or revision-checked (`ROOT_BINDING_MISMATCH`) until `initializeRootBinding` runs. Additive for callers: `PurgePreview`, `ProposalPurgePreview`, `PurgeOptions` and `StaleRevisionError` are new exports. Breaking for a host that implements `KnowledgeStorePurger` itself (the bundled adapters need nothing): add `previewPurge` and `previewPurgeProposal`, and make `purge` and `purgeProposal` accept `{ expectedRevision }` and throw `STALE_REVISION`, writing nothing, when it no longer matches; the new `purge-preview-*` vectors fail it until it does. `@kontourai/corpus-conformance` adds eighteen `purge-preview-*` vectors, so corpus-store now runs 209 store vectors per profile. `npm run proof:preview` in `packages/store` reproduces the fault injections, and `proof:purge` gains `--check-compiles`.
- **corpus-store: records can carry a `confidence` from 0 to 1** ([#68](https://github.com/kontourai/corpus/issues/68)). A writer can now record how sure it was by passing `confidence` (0 to 1 inclusive) to `create`, `proposeCreate` or `update`. It is optional on `CreateInput`, `UpdateFields` and `KitRecord`, works for any record type, is stored as a plain frontmatter number, and reads back exactly on both profiles. `create`, `proposeCreate` and `update` refuse a value below 0 or above 1, `NaN`, an infinity and any non-number with `MISSING_EVIDENCE` and write nothing; nothing is clamped, and `-0` is stored as `0`. `update` clears it with `null`. It is part of a proposal's request digest: a keyed retry that changes, adds or drops it is `REQUEST_KEY_CONFLICT`, and an identical retry returns the original proposal. Purging a record, a cascade and `purgeProposal` erase it; a record a cascade leaves in place because other sources still support it keeps it. Additive for writers. Two edge cases are not: a note on disk whose `confidence` is not a number in range (a hand-written `confidence: high`, which was an untouched unknown field before) is now corruption when read, and a vault `dimensions` entry named `confidence` is refused at construction because it would overwrite the field. `@kontourai/corpus-conformance` adds eleven `confidence-*` vectors and lets a vector write `{"$number": "NaN" | "Infinity" | "-Infinity" | "-0"}` for the numbers JSON cannot. `npm run proof:confidence` in `packages/store` reproduces the fault injections.

## 0.1.0-next.2

- **corpus-store: `purgeProposal` erases a create proposal by its own id** ([#62](https://github.com/kontourai/corpus/issues/62)). `KnowledgeStorePurger` gains `purgeProposal(proposalId, { agent, rationale, note? })`, gated by `allowPurge: true` like `purge`. It erases a pending, rejected or applied proposal (candidate, evidence text, `source_refs`, link labels, a reviewer's rationale) into the same stub and `erasure` marker a record purge writes, settles a pending one as `rejected`, purges the record an applied proposal created in the same transaction, is idempotent (`alreadyErased`), and is applied whole or rolled back whole if interrupted. A request-key retry after it is refused with `REQUEST_KEY_CONFLICT`. Additive: `ProposalPurgeResult` is a new exported type, and the `purge-proposal-erase-*` conformance vectors (ten, including probes) join the store vectors.

## 0.1.0-next.0

- Extracted from Station with injected host services ([#14](https://github.com/kontourai/corpus/pull/14)), and prepared for trusted publication ([#17](https://github.com/kontourai/corpus/pull/17)).
- Preserve named vault dimensions across category changes ([#35](https://github.com/kontourai/corpus/pull/35)).
- Transactional create proposals ([#42](https://github.com/kontourai/corpus/pull/42)), deduplicated by request key ([#49](https://github.com/kontourai/corpus/pull/49)).
- Purge with tombstones and a sole-dependency cascade ([#41](https://github.com/kontourai/corpus/pull/41)).
- Write the empty path index when reindex finds no vault records ([#50](https://github.com/kontourai/corpus/pull/50)), and refuse vault records larger than the note read bound ([#52](https://github.com/kontourai/corpus/pull/52)).
- Conformance: `decision-records.json` and vectors for the decision-record secret detectors, which the root CLI's decision registry gate uses (see the root changelog, `0.8.0`).
- **Breaking (corpus-store): canonical vault index and `corpus-store migrate`.** The vault adapter now selects its path index on every operation. `path-index.json` is canonical. A vault with only the Knowledge Kit's `.graph-index.json` (`kit-v1`) opens read-only: reads work and every mutation throws `READ_ONLY`. Both files at once is refused as a conflict. A root that already holds store data but has neither index is refused instead of being read as an empty vault; an empty root or plain notes still open as a new vault. The package gains a `corpus-store` bin: `corpus-store migrate <vault-root> [--check | --reverse]` converts a `kit-v1` vault offline in one journaled transaction, writes a hashed manifest and the original index under `.corpus-store-migration/`, verifies every other file's bytes and every record through the vault adapter, and reverses only while the bytes still match. `ReadOnlyStoreError` takes an optional reason.
- **Breaking (corpus-store): a compiled record must link a raw source when it is created.** `create` with `type: 'compiled'` requires a link of kind `source` to an existing `raw` record, or throws `MISSING_EVIDENCE` and writes nothing. `provenance.source_ids`, `related` links and wikilinks do not count. Existing source-less compiled records stay readable, listable and updatable. The last vector leaves the expected-fail list, which is now empty: corpus-store passes all 123 store vectors on both profiles.
- **Breaking (corpus-store): one expiry rule and an expiry-only stale filter.** A record expires at its explicit `expires_at`, otherwise `ttl_seconds` after `created_at` (never reset by an update); a record with neither never expires, and expiry is inclusive. `listByType` and `listByCategory` take `stale` (`true`: only expired; `false`: only unexpired; omitted: no expiry filter) and `now` (epoch milliseconds, defaulting to the store clock); a non-boolean `stale` or non-finite `now` is refused with `MISSING_EVIDENCE`. Previously these options were ignored. Three vectors leave the expected-fail list (4 to 1).
- **Breaking (corpus-store): lists return the working set; `includeHistory` is the one history flag.** `listByType` and `listByCategory` omit retired and superseded records unless `includeHistory: true` is passed, in both profiles. The default profile previously listed superseded records; it no longer does. The vault's history now walks archived (superseded) notes, which `includeRetired` never reached. `includeRetired` is a deprecated alias translated to `includeHistory: true`, so it now also returns superseded records. `implemented` records stay in the working set. Callers that need superseded records in a list (for example, consolidation over earlier snapshots) must pass `includeHistory: true`. Three vectors leave the expected-fail list (7 to 4).
- **Breaking (corpus-store): proposals may target any record type.** `propose`, `apply` and `reject` accept a target of every record type, not only `concept`, by the owner's 2026-10-13 decision. The target and proposer must still exist, evidence is still required, and `apply` and `reject` still require the proposer's `proposes` link. A caller that relied on `MISSING_EVIDENCE` for a non-concept target now succeeds instead. Stored mutation-log evidence keeps its `concept_id` key. Twelve vectors leave the expected-fail list (19 to 7).
- **Store conformance: host vectors.** A conformance vector may declare `"scope": "host"` when it needs behavior a store library does not implement. `search-working-set` is the only one: it moves out of corpus-store's expected-fail list, which could otherwise never become empty, and becomes an obligation that every host mounting the store must pass. `@kontourai/corpus-conformance` exports `storeVectors`, `hostVectors` and `vectorScope`; an unknown scope fails at import. corpus-store's runner executes only store vectors (123), refuses a selected host vector, and fails if its expected-fail list names one. The list drops from 20 to 19 entries.
- Public store conformance vectors require `MISSING_EVIDENCE` for duplicate IDs, including reuse after retirement. The runner rejects malformed expected entries without `equals` or `length`.
